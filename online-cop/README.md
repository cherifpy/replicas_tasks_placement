# Online COP (Choco-solver + LNS, no reconsideration)

Implementation of the **Online COP** approach from the paper (Section 4.1): on every job
arrival, (re)plans in a single CP solve every job not yet fully assigned (the newly
arrived one + those already running with tasks still `NotStarted`), feeding the model an
**estimate of when each node will free up** (`nodesFreeTime` - based on its current
transfer/task, no assumption about the future beyond that) instead of the full horizon
the way Offline COP does.

**No reconsideration**: a task that has already started (`status == "Started"`) is never
revisited - only the assignment of tasks still `NotStarted` can change from one solver
call to the next. This is what distinguishes this approach from Offline COP (which
recomputes everything, over the whole horizon, in a single solve fixed at the start).

Copied/adapted from `simulator-for-CSP-model/simulator/` (separate Python project):
`master_node_with_heterogeneous_nodes_csp.py` (class `SchedulingUsingCSPOnline` - only
the base Online variant is kept here, not WarmStart/ThreeStep/Incremental/SemiOnline,
which reconsider or otherwise change this behavior) and `utils/modelCSP.py` (bridge to
the Java solver, trimmed down to what `MainOnline.java` actually reads - see
`modelCSP_online.py`). The Java model itself (`utils/model/src/main/MainOnline.java`) is
copied as-is.

**Model scope**: like the Heuristic and Offline COP, the traces used here (`../traces/`,
generated by `../generate_traces.py`) have unlimited `storage_capacity` - the paper does
not model a storage constraint.

## Contents

**Python side (SimPy, same pattern as `../run_heuristic.py`):**
- `job.py`, `tracker.py`, `compute_node.py` - base classes (copied from
  simulator-for-CSP-model/, **different** from those used by the Heuristic: this
  approach models a node that can host several datasets at once (`node.datasets`, a
  list) rather than just one at a time (`node.current_dataset`), and
  `compute_capacity` here is a MULTIPLICATIVE factor (`task_duration = duration *
  capacity`) rather than a divisor - two different representations of the same final
  computation, not an inconsistency).
- `master_node_online.py` - `SchedulingUsingCSPOnline`: SimPy loops (job arrivals,
  triggering a solve, dispatching the planned tasks/transfers, detecting job
  completion).
- `modelCSP_online.py` - serializes the current state to `utils/model/inputs/*`,
  invokes `javac`/`java` on `MainOnline`, reads its plan back from
  `utils/model/outputs/*.csv`.
- `run_online_cop.py` - runner: loads an instance (`../traces/inst-XJ-YN/`), wires
  everything above together, reports `avg_flow_time_s`, `nb_transfers`, etc.

**Java side (CP model):**
- `utils/model/src/main/MainOnline.java` - the model (Choco-solver + LNS), copied as-is
  from the separate repo.
- `utils/model/lib/` - vendored jars (same as `../offline-cop/lib/`: Choco-solver
  5.0.0-beta.2 "light", org.json) - no Maven Central dependency needed.
- `utils/model/inputs/`, `utils/model/outputs/`, `utils/model/bin/` - exchange files /
  compiled classes, regenerated on every call (see `modelCSP_online.py`) - empty at the
  start, nothing to commit there.

**Requirements**: Python 3.10+ (`pip install simpy numpy pandas`), JDK 17 or newer (LTS
recommended: 17, 21 or 25 - tested with JDK 25.0.1) and `javac`/`java` on the `PATH`
(invoked as subprocesses by `modelCSP_online.py`, same as the original repo).

**Choco-solver documentation** (to understand/modify `MainOnline.java`): see
`../offline-cop/README.md` (same vendored jars, same 5.0.0-beta.2 version) - official
site https://choco-solver.org/, Javadoc
https://javadoc.io/doc/org.choco-solver/choco-solver/5.0.0-beta.2/index.html, repo
https://github.com/chocoteam/choco-solver.

## Usage

```bash
cd simulator/paper-artifact/online-cop

python3 run_online_cop.py ../traces/inst-10J-50N
ONLINE_COP_SOLVER_TIME_LIMIT_S=15 python3 run_online_cop.py ../traces/inst-20J-50N
```

`ONLINE_COP_SOLVER_TIME_LIMIT_S` (or `--solver-time-limit`, default **5** seconds):
time budget granted to **each call** of the Java solver. A call happens on every
(re)planning - at least once per arriving job, potentially more for a multi-task job
while its placement keeps being recomputed before all its tasks are dispatched. A
larger budget improves the quality of each individual solution, but the total
(wall-clock) time of the simulation grows with the number of calls - keep a modest
value (a few seconds) for a quick demo, increase it to get closer to the paper's
conditions. In practice the solver often returns well before the limit (as soon as it
finds/proves a solution good enough for the small batch of a single tick), so the
observed real time is generally well below `nb_calls x limit`.

`ONLINE_COP_OBJECTIVE` (default **0**): which `objectives[i]` the solver minimizes on
each call - `0` = sum of flow times of the current batch (comparable to
`avg_flow_time_s` of the other two approaches), `1` = max flow time of the batch, `2` =
flow time of the newly arrived job alone. The original Java file defaults to `1`; this
artifact forces `0` by default so the 3 approaches are comparable on the same metric.

Output (example):

```
            instance: inst-10J-50N
    nb_jobs_finished: 10
     avg_flow_time_s: ...
   amount_of_data_MB: ...
        nb_transfers: ...
```

`avg_flow_time_s` is directly comparable to the metric of the same name reported by
`../run_heuristic.py` (Heuristic) and `../offline-cop/RunOfflineCOP` (Offline COP), on
the same instance.

## Correspondence with the paper

| Paper concept | File / function |
|---|---|
| Online COP (Section 4.1): (re)planning on each arrival, without reconsidering work already started | `master_node_online.py` -> `SchedulingUsingCSPOnline.schedulingNewJob`/`scheduling` |
| Estimate of node free time fed to the solver | `master_node_online.py` -> `SchedulingUsingCSPOnline.nodesFreeTime` |
| CP model (Choco-solver + LNS) solved on every call | `utils/model/src/main/MainOnline.java` |
| Python <-> Java bridge (serialization/deserialization) | `modelCSP_online.py` -> `schedulingUsingJavaCSP` |

The `WarmStart`/`ThreeStep`/`Incremental`/`IncrementalFreeNodesOnly`/`SemiOnline`
variants from the separate repo (side experiments, not in the paper) are **not**
included here.
